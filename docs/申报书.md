# moonkube 项目申报书

**项目名称**：moonkube —— 纯 MoonBit 实现的 Kubernetes API 客户端与 Controller 框架
**仓库**：https://github.com/Rz-coder8848/moonkube
**方向**：云原生基础设施 / 集群客户端基础库
**性质**：原创实现（依据 Kubernetes 公开 API 规范与对象语义，非代码移植）
**许可证**：Apache-2.0

## 一、项目简介

moonkube 用 MoonBit 从零实现"与 Kubernetes 集群对话"的那一层：kubeconfig 解析、类型化资源模型、精确数量运算、标签/字段选择器、三种 Patch 语义、watch 事件流与断点续传、List-Watch 缓存（Informer）、WorkQueue 与 Reconcile 循环。协议层零 IO，全部逻辑可在无集群环境下测试。

## 二、痛点与生态定位

MoonBit 的 core 标准库没有任何 socket / HTTP / 集群工具，mooncakes.io 现有 2564 个包中 `kube`、`kubernetes`、`k8s`、`informer`、`reconcile` 关键词**命中数为 0**——这个方向是完全空白的。结果是：任何想跑在集群里、或想驱动集群的 MoonBit 服务，都只能自己重写一遍协议，而 Kubernetes 的协议恰恰是"看起来简单、语义处处有坑"的那一类。

本项目补的是**语义层**，不是又一个 HTTP 封装：把容易做错、且做错之后会静默出错的地方固化成可测试的库。

## 三、使用场景

1. **集群内运维工具**：用 MoonBit 写一个巡检程序，列出所有 Node 的容量与已分配资源，按 CPU 余量排序。数量必须按值比较（`1000m` 与 `1` 相等），字符串比较会给出错误结论。
2. **自定义 Controller**：监听 Deployment 变化，确保每个命名空间都存在一个指定 ConfigMap。需要 List-Watch 缓存一致、`resourceVersion` 断点续传、以及队列去重与退避重试。
3. **CI / 发布流水线**：在流水线里做滚动更新前的预检——按标签选择器挑选工作负载、读取配额、用 Merge Patch 打补丁，并把 API 返回的 409 冲突与 403 权限错误区分为"重试"与"报错"。

## 四、核心功能与交付边界

**交付**：kubeconfig（JSON + kubeconfig 专用最小 YAML 子集）；类型化资源（Pod / Deployment / Service / ConfigMap / Secret / Namespace / Node / Job 等）与保留未知字段的 DynamicObject；Quantity 精确运算与 kubectl 一致的规范化输出；标签/字段选择器；JSON Patch、JSON Merge Patch、Strategic Merge 的 map 合并子集；watch 事件解码与 410 重列；Informer、WorkQueue、Reconciler；可运行 CLI 示例与录制回放。

**明确不做**：真实 TCP/TLS 传输（core 无网络包，通过 `Transport` trait 留出接入点，不藏 FFI）；`exec` / OIDC 等认证插件；`kubectl apply` 的完整三路合并语义；通用 YAML 解析器（只覆盖 kubeconfig 结构）；CRD schema 校验。

## 五、实现路径与技术理解

**常见路径**：①用 FFI 包住 client-go；②只做 HTTP 包装；③重写协议与语义层。前两者在 MoonBit 里都会把平台差异和语义错误带进调用方，第三种最慢但最干净，也是本项目选的路径。

**三个决定成败的细节**：第一，Quantity 必须用任意精度整数按值比较，`1000m == 1`，且 `2Ei`、`1e100` 不能溢出；第二，选择器的 `!=` 与 `notin` 对"键不存在"的对象也成立，做错会静默漏掉服务端本该返回的对象；第三，watch 断线必须带 `resourceVersion` 续传，收到 410 要重新 List 而不是重试。

**传输层边界**：core 没有网络能力，所以把 IO 收进一个 `Transport` trait，之上全部是纯函数。这既让测试不依赖集群，也让未来接 TCP/TLS 只需实现一次 trait。
